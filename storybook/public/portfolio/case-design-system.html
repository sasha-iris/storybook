A component library developers can copy from

Forty-seven components documented so that what you see in the story is the class that ships. Most of the work was an audit, and most of the audit was saying no.

Role
Sole designer — Figma extraction, CSS, stories, documentation
Product
Financial analytics platform for ecommerce brands
Consumers
Storybook, the production CSS bundle, and a low-code build environment
Live
The library, running

The problem

The library looked finished. Every component family had stories, the sidebar was full, and the site built cleanly. The question nobody had asked was narrower and more awkward: if a developer copies what a story shows, do they get the component?

Often they did not. A story could be drawn with inline styles and no signature class in the markup, which makes it a picture of a component rather than the component. The audit I wrote defines the failure state in one line: the preview is not the component, so it cannot be handed to developers as it stands.

So I extracted all 447 classes from the shipped CSS and checked each family against them, by computed style in the browser rather than by eye. Twelve families failed. Those twelve were rebuilt on the real classes; the rest were spot-checked and left alone.

Open the library → 47 components, 249 stories, tokens and interactive controls. Every story carries a three-tier code snippet: HTML, the class list, and the React wrapper.

Decisions

Structure

One top-level slot per family, and no Components/ wrapper

The wrapper folder was removed on purpose and the rule written into the project's own instructions with a wrong-example beside it, because a convention that only lives in someone's head gets undone by the next person who adds a story. Flat by family means every component sits at the top level of the sidebar, so there is one place to look for it.

Refused

Deleting components that were never designed

A KPI card, a set of datepicker presets, a metric card and several select and search types existed in the stories but not in Figma. Someone had invented them while documenting. I deleted them rather than backfill designs, and made the rule explicit: if it is not in Figma, it does not go in Storybook.

Refused

Deleting CSS that looked orphaned

Seven banner rules, eight drawer rules, five range-slider rules and thirteen select rules had no story and no page using them. The tidy move is to delete them. I left them, because the low-code environment consumes the same file and I could not see inside it. They are documented as orphaned, with the three consumers of the file named, so the deletion can be made by someone who can see inside all three.

Accepted a limit

The Actions tab does not work here, and four attempts is enough

Interaction logging never worked in this static build. I tried four approaches, wrote down what each one did, and then wrote down that the next person should not spend time on it without browser access. Controls, docs and source snippets deliver more, so the four attempts are written up as a known limitation with the reason each one failed.

Accessibility

Fixing the success green in the token

The success green failed contrast at 3.0:1 on white. It would have been faster to darken it on the page that surfaced it. Instead the token itself moved to #007a55, and the comment recording why sits in the token file where the next person will see it. The same pattern repeats through the work: the collapsed sidebar lost its hardcoded white background because that background broke dark theme, and three components stopped hardcoding a system font stack because the product's font is set higher up.

Content

Real content in every story

Placeholder text hides the problems a story exists to expose: truncation, wrapping, spacing under a long label. This one is written into the project's story patterns as a rule, next to the argTypes template, because it is the kind of shortcut that gets taken under time pressure by whoever documents the next component.

Consistency

Two CSS files, one truth

The preview and the export consume different files, so any change has to land in both in the same commit. Auditing the pair turned up six token conflicts and a legacy duplicate block. One of them, a blue-versus-purple --color-bg-primary, was already breaking form checkboxes.

What using it revealed

The library got its real test when I built product pages using nothing but its classes. That rule — zero custom CSS on consuming pages — turns every gap into a recorded finding instead of a private workaround.

It found real ones. The drawer component was not usable, so a page that wanted a drawer used a modal and the gap was written down. A progress bar had no danger variant, so a “broken” state had been coloured with a chart palette pink that means “trend down”, not “error”. Two colour tokens measured below AA at the sizes the pages actually used them. None of that is visible from inside Figma.

Handoff

The library is consumed by three different things, so the documentation is written three ways: a copyable snippet on every story, a per-component reference for the low-code environment, and a set of thin React wrappers with a stated boundary — each one says what to use it for, what not to, and which existing component it replaces. Charts and complex data grids are explicitly out of scope and point at other libraries.
